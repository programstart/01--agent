## 1. 技术基线

第一阶段采用：

- Python 3.11+；
- CLI 作为运行入口；
- SQLite 作为本地关系型数据库；
- LangGraph 作为 Agent 工作流和 ReAct 循环执行框架；
- Pydantic 2 作为输入、状态和工具输出校验层；
- 模型适配层支持真实模型和离线 Mock 两种实现；
- pytest 执行自动化验收。

采用 LangGraph 不是依靠框架名称获得评分，而是利用显式的 Graph State、条件路由和工具循环降低实现与调试成本。项目仍自定义业务状态、工具边界、Guard、Trace 和停止条件，不依赖隐藏的预置提示词。详细取舍见 [technology-stack.md](technology-stack.md)。

## 2. 总体架构

```text
CLI 输入
   │
   ▼
请求规范化与幂等键计算
   │
   ▼
LangGraph ReAct Runtime ───► 模型适配层
   │                            │
   │ Graph State 和工具观察     │ 选择下一个合法动作
   ▼                            ▼
工具执行器 ◄────────────────────┘
   │
   ├── read_material
   ├── check_audit_rules
   ├── query_schedule_slots
   └── save_schedule_draft
   │
   ▼
SQLite：素材、规则、排期、草稿
```

LangGraph 负责执行循环、状态传递和条件路由；程序负责数据访问、约束校验、步数限制和数据库事务；模型负责根据当前观察结果选择下一步合法动作。

## 3. 组件职责

| 组件 | 职责 |
| --- | --- |
| CLI | 接收素材 ID、时间和时区，输出最终结果和 Trace 位置 |
| 请求规范化器 | 校验字段、统一发布时间格式和时区 |
| LangGraph Runtime | 维护 Graph State、执行 ReAct 循环、调用模型和工具、执行条件路由 |
| 模型适配层 | 在真实模型与离线 Mock 间切换，返回结构化动作 |
| 工具执行器 | 校验参数、调用工具、记录公开 Trace |
| Guard / Stop Policy | 独立检查模型步骤、工具次数、无进展和未完成状态 |
| Trace Mapper | 把 LangGraph 事件转换为题目要求的公开执行记录 |
| SQLite 数据层 | 保存合成素材、规则、已有排期和可写草稿 |

模型不直接连接数据库，不生成 SQL，不自由读取任意表，也不能调用未注册工具。

## 4. 数据模型

### 4.1 素材

使用现有的 [素材读取工具设计](material-read-tool.md)。核心字段包括：

- `asset_id`
- `title`
- `platform`
- `source_status`
- `content`
- `metadata_json`
- 可选 `version` 和 `updated_at`

素材读取为只读操作。版本不是第一阶段必填字段；判断数据是否变化时，可优先使用数据源提供的版本或更新时间。

### 4.2 审核规则

审核规则使用统一的 v2 结构，至少包含：

- `rule_id`
- `rule_kind`：`STRUCTURED` 或 `SEMANTIC`；
- 风险等级：`WARNING` 或 `BLOCKING`；
- 适用平台或素材类型；
- 生效时间；
- 自然语言规则原文；
- 结构化规则条件；
- 面向用户的风险原因；
- 规则是否启用。

结构化规则由程序按白名单字段和确定操作符执行。语义规则将完整当前素材和自然语言规则交给结构化语义审核器，并返回规则结论、原因和原文证据。

两类规则都输出统一的 `RuleEvaluation`。程序校验规则 ID、规则等级和证据真实性，并聚合为 `PASS`、`WARNING`、`NEEDS_INFO`、`NEEDS_REVIEW`、`BLOCKED` 或 `ERROR`。

关键词或正则未命中只能说明相应结构化规则未命中，不能证明整体语义合规。

### 4.3 排期

排期记录使用连续时段表示占用。每个请求默认从 `publish_at_utc` 开始占用 30 分钟，冲突判断以同一 `scope_id` 下的半开区间是否重叠为准。

第一阶段识别以下状态：

- `CONFIRMED`：已确认排期，硬占用；
- `PUBLISHED`：已发布，硬占用；
- `CANCELLED`：已取消，不占用。

已有有效草稿作为软占用参与区间查询，但不能覆盖确认排期。

### 4.4 草稿

草稿至少包含：

- `draft_id`
- 唯一 `idempotency_key`
- `asset_id`
- 原始请求快照；
- 用户原始要求开始时间和建议发布开始时间；
- 默认 30 分钟的占用时长；
- 时区；
- 审核结果快照；
- `PENDING_CONFIRMATION` 或 `READY` 状态；
- 创建时间。

相同幂等键必须有数据库唯一约束。第一阶段不自动删除、覆盖或迁移旧草稿。

## 5. 工具设计

四个业务工具均为高层工具，模型只提供业务参数，底层数据库访问由运行时完成。

| 工具 | 输入摘要 | 输出摘要 | 副作用 |
| --- | --- | --- | --- |
| `read_material` | `asset_id` | 素材、完整性、错误 | 无 |
| `check_audit_rules` | 素材 ID 和当前请求快照 | 审核状态、统一规则结果、证据和摘要 | 无 |
| `query_schedule_slots` | 发布开始时间、时区、30 分钟占用配置、查询边界和幂等上下文 | 区间冲突、结束时间和有限替代时段 | 无 |
| `save_schedule_draft` | 幂等键、素材、建议开始时间、30 分钟占用和待确认项 | 新草稿、已有草稿或保存失败 | 写入草稿 |

`read_material` 的详细契约见 [material-read-tool.md](material-read-tool.md)，`check_audit_rules` 的详细契约见 [rule-engine-v2.md](rule-engine-v2.md)，`query_schedule_slots` 的详细契约见 [schedule-query-tool.md](schedule-query-tool.md)，`save_schedule_draft` 的详细契约见 [save-schedule-draft-tool.md](save-schedule-draft-tool.md)。

### 允许的 Agent 动作

- `read_material`
- `check_audit_rules`
- `query_schedule_slots`
- `save_schedule_draft`
- `finish`

运行时根据当前状态限制可执行动作。例如资料不足时不允许查询时段，审核阻断时不允许保存草稿。
需要用户补充资料或确认时，运行时结束当前自动流程，并在最终报告中保留缺失字段、原始时间要求和待确认原因。

## 6. Agent 决策循环

使用 LangGraph 的 ReAct 工具循环作为执行骨架。每次模型调用只返回一个结构化动作，LangGraph 根据动作路由到相应工具节点；工具观察结果写回自定义 Graph State，再回到模型决策节点，直到完成、需要用户输入、达到上限或工具失败终止。

项目自定义扩展包括：

- Graph State 中的素材、审核、时段、草稿和预算字段；
- 工具包装层的参数校验和 Trace；
- 模型调用前和工具调用后的 Guard；
- 正常、冲突、阻断、工具失败和未完成路由；
- 框架事件到题目输出结构的转换。

### 正常路径

1. 规范化用户请求并计算幂等键。
2. 查询是否已有相同请求的草稿。
3. 没有草稿时调用 `read_material`。
4. 素材完整时由模型选择 `check_audit_rules`。
5. 审核通过或仅警告时由模型选择 `query_schedule_slots`。
6. 目标 30 分钟时段可用时由模型选择 `save_schedule_draft`。
7. 返回草稿 ID 和当前状态，结束。

### 冲突路径

1. 目标 `[开始时间, 开始时间 + 30 分钟)` 与已有排期重叠。
2. `query_schedule_slots` 从原请求起每 30 分钟向后查找，返回有限替代时段。
3. 模型选择保存替代时段草稿或请求确认。
4. 草稿标记 `PENDING_CONFIRMATION`。
5. 原精确开始时间保留在原始请求中，不能被覆盖。
6. 如果查询范围内没有可行时段，返回未完成及冲突原因。

### 资料或规则异常路径

- 素材不存在或字段缺失：请求用户核对或补充，停止排期；
- 规则警告：可在待确认状态下保存草稿；
- 规则阻断：停止排期，不保存可发布草稿；
- 工具失败：仅对允许重试的错误执行一次有限重试；
- 无进展或达到预算：停止并返回 `INCOMPLETE`。

## 7. 幂等与重复提交

### 幂等键

第一阶段建议由运行时根据以下稳定业务字段计算：

- 用户或工作区；
- 素材 ID；
- 原始发布时间要求；
- 请求动作类型。

模型生成的说明、推理、Trace、替代时段文案和草稿 ID 不参与幂等键。

### 重复提交

1. 先按幂等键查询草稿。
2. 找到后仍重新执行素材读取、规则检查和时段查询。
3. 当前检查允许继续时，保存工具返回 `EXISTING` 和原草稿 ID，不新增记录。
4. 当前审核阻断或没有可保存时段时，本次运行返回未完成，旧草稿保持不变。
5. 用户改变时间时生成新的请求身份并执行完整检查。
6. 第一阶段不自动比较历史快照、迁移或覆盖旧草稿。

### 新运行

每次新运行都使用当前数据库快照，不复用上一进程内的内存结论。素材版本不是必需条件；没有版本字段时，以本次读取的允许字段作为当前审核快照。

## 8. 冲突与选择规则

第一阶段处理“当前请求”和“已有排期”之间的冲突：

1. 素材被审核阻断时不能排期。
2. `CONFIRMED` 和 `PUBLISHED` 已占用区间优先于新请求。
3. 精确开始时间属于硬性要求，不能静默改变。
4. 冲突后可以从 30 分钟后开始提出替代时段，但必须标记待用户确认。
5. 同一请求自身的草稿不计入冲突。
6. 查询不到可行替代时段时返回 `NO_FEASIBLE_SLOT`。
7. 多素材批量竞争和业务优先级分配不在第一阶段自动处理。

草稿保存与冲突检查的事务边界：

- 重新读取并按 30 分钟区间确认目标发布时段；
- 校验幂等键；
- 写入草稿；
- 任一步失败则回滚；
- 只有事务成功后才向用户返回草稿 ID。

## 9. 运行状态与停止条件

运行状态至少包含：

- 规范化后的用户请求；
- 当前幂等键；
- 当前步骤和剩余预算；
- 素材读取结果；
- 审核结果；
- 时段查询结果；
- 建议草稿内容；
- 待确认事项；
- 已使用的工具参数和观察摘要；
- 最终状态。

停止条件：

- 草稿成功保存或复用；
- 需要用户补充信息或确认；
- 审核阻断；
- 没有可行时段；
- 工具失败且达到重试上限；
- 相同动作和结果重复且没有状态变化；
- 达到 8 个模型步骤或 6 次业务工具调用。

## 10. 失败处理

| 失败 | 处理 |
| --- | --- |
| 参数非法 | 不执行工具，说明错误字段 |
| 素材不存在 | 不创建草稿，请用户核对 ID |
| 资料不足 | 返回缺失字段，不继续排期 |
| 规则阻断 | 返回规则 ID 和原因，不保存可发布草稿 |
| 时段冲突 | 返回重叠区间、开始/结束时间和替代方案，保留原始要求 |
| 重复提交 | 返回已有草稿，不新增记录 |
| 草稿保存失败 | 回滚并返回失败 |
| 模型不可用 | 可运行离线 Mock 仅用于验证流程，并明确标注边界 |
| 达到执行上限 | 返回 `INCOMPLETE` 和未完成原因 |

## 11. Trace 与验证

Trace 记录公开执行信息：

- 步骤编号；
- 选择的动作和工具；
- 工具参数；
- 返回状态和必要摘要；
- 后续动作；
- 简要决策依据；
- 幂等键和草稿 ID 的脱敏摘要；
- 运行完成或未完成状态。

不记录模型内部思维过程、完整素材正文、API 密钥或数据库连接信息。

第一阶段至少提供：

- 一条正常保存草稿路径；
- 一条时段冲突并生成待确认草稿路径；
- 一条资料不足、规则阻断或工具失败路径；
- 自动化测试结果；
- Mock 与真实模型能力的边界说明。

## 12. 实施顺序

1. 确定请求、工具和结果的数据结构。
2. 建立 SQLite 表结构与合成种子数据。
3. 实现四个工具及其测试。
4. 搭建 LangGraph ReAct 图、自定义 Graph State、模型适配层、工具包装和停止条件。
5. 实现 CLI 与结果输出。
6. 完成正常、冲突、资料缺失、重复提交、保存失败等验收。
7. 生成 `examples/` 下的实际输入、输出和 Trace。
8. 补充评估、AI 使用记录和复盘文档。

当前代码、测试、示例和交付文档已按上述方案实现。
