# 第 1 题：阶段复盘

> 更新日期：2026-11-01

## 1. 最关键的问题

### ReAct 不能退化为固定流水线

题目要求模型根据工具结果调整动作。最终实现把动态选择放在 `model_decide`，LangGraph 条件边再执行工具。正常路径和冲突路径的差异来自时段查询观察，而不是输入时间的人为分支。

### 外部状态必须可信

模型不能自行修改审核结果、幂等键、确认原因或发布状态。这些内容由 Runtime、数据库和确定性服务产生，模型只选择下一步动作。

### 时间语义必须明确

第一阶段把每个发布请求建模为默认 30 分钟的半开区间，统一转换到 UTC 后判断区间是否重叠。`18:00–18:30` 与 `18:30–19:00` 可以相邻；发生冲突后从原请求开始每 30 分钟向后查找替代时段。

### 重复保存与并发冲突

草稿保存使用运行时幂等键、SQLite 唯一约束和写事务。保存前再次检查目标 30 分钟区间，避免查询与写入之间存在竞争。

### 规则与语义审核的边界

最初版本使用关键词和字段规则，只能证明已配置规则没有命中，不能证明整体内容合规。规则引擎 v2 将结构化规则和自然语言语义规则统一为同一结果结构，并增加证据存在性和语义支持校验。模型负责语义判断，程序负责规则 ID、严重等级、原文证据和最终状态。

## 2. 设计取舍

- 使用 LangGraph 状态图管理循环和路由；
- 保留自定义 Guard，不只依赖框架执行限制；
- 使用 Pydantic 定义稳定 DTO；
- 业务工具全部确定性实现；
- 模型适配层同时支持 Mock 和真实模型；
- 不为第一阶段增加 UI、多 Agent 或生产部署。

## 3. 学习收获

- ReAct 的可靠性更多来自外部状态、工具边界和停止条件，而不是模型自由度；
- 确认状态、保存状态和发布状态必须分开建模；
- 幂等逻辑必须在数据库事务内执行；
- Mock 对自动化测试有价值，但不能替代真实模型效果验证；
- 工具输出应足够结构化，方便模型决策和测试断言。
- 不确定语义不能依靠关键词穷举，确定事实也不能依赖模型保证；
- 语义审核必须返回可定位原文，否则不能作为阻断或通过依据。
